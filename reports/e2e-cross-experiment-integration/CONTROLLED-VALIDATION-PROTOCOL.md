## New question: does the reviewed treatment close the identified route gap?

The comparison should test F2–F4: whether the actual greenfield route activates supported progress controls, retains final context feedback, accepts schema-valid evidence requests and progresses to legitimate mutation. Merely getting further than historical Run-006 would not isolate these causes. This is a design for future authorization, not a run command or an executed trial.

## Freeze a matched Before, rather than relabel historical Run-006

Run-006 used base `f842fb8` plus five local production deltas, including two subsequently withheld ingestion rewrites. Replacing those with safer corrections changes the state that produced the original failure. The existing trace is an historical reference, not automatically the controlled Before arm.

Prefer a newly agreed common source revision containing the reviewed startup and regression-safe ingestion prerequisites. Define:

| Arm | Source and configuration | Permitted interpretation |
|---|---|---|
| **Before A** | Common executable revision and fixed effective policies | Establish actual route activation, current behavior and available downstream boundaries on that revision. |
| **After B** | Same common revision plus only the reviewed treatment, with the same policies unless policy selection itself is the declared treatment | Compare the specifically changed mechanism. Preserve all failures and missing observations. |
| **Optional integration arm C** | A separately agreed supported policy combination | Evaluate combined integration; changing multiple policies does not isolate one causal fix. |

An exact archived-source replay is a different diagnostic design: it would retain the withheld rewrites in an isolated experimental reference, explicitly unverified and never promoted as product fixes. It is not authorized or prepared here. Do not silently substitute PR #2's head, fork `main`, or a teammate's unmerged branch for the historical source.

## New observations required at the integration boundaries

| Finding tested | Required capture | Falsifiable success condition and limit |
|---|---|---|
| Contract/route activation | Project mode, contract presence/identity, applicable authority, wrapper activation or explicit non-activation reason | The intended greenfield path actually activates the reviewed mechanism. A supplied synthetic contract is not equivalent. |
| Progress after sufficient context | Offered tools before/after the gate, context state, repeated checks, first attempted/applied mutation and remaining budget | Repetition is controlled as specified without weakening gates. An earlier safe stop can pass a progress-control assertion while still failing artifact delivery. |
| Feedback retention | Bounded next-request capture or field-presence/retention assertions for long mission text | Required obligations and final gate feedback survive the actual projection. Token estimates alone cannot prove this. |
| Schema alignment | Requested evidence kinds, validator outcome, returned evidence and subsequent decision | Publicly valid supported requests execute meaningfully; invalid requests remain bounded and clearly rejected. Authorization without evidence acquisition is not semantic sufficiency proof. |
| Mutation/recovery | Exact observed source, source identity, allowed surface, edit result and refresh/active-tool correspondence | Real agent-generated edits obey grounding and authority; stale anchors are rejected and valid refresh recovery is exercised if reached. |
| Downstream integration | Actual profile, executed behavior, evidence aggregation, receipt identity and fresh parent checks where applicable | No downstream stage is credited from source presence, flags or cached child proof. Unreached stages remain untested. |

Capture instrumentation consistently across both arms. New logging must be reviewed for observational equivalence and privacy; do not introduce model-visible guidance into only one arm and call it passive observation. Preserve full native outcomes and clearly label any interrupted root or incomplete capture.

## Decision and stopping protocol

Define time/tool limits and root stopping conditions before execution. Distinguish the first completed child failure from later recursion and investigator interruption. No automatic repair by the validator, fake tool success or manual application implementation is permitted.

If an artifact exists, execute the unchanged independent acceptance criteria through real keyboard/touch and gameplay transitions, including repeated restart, persistence/reload/storage denial and terminal-state freezing. Check adapters against actual gameplay. If no artifact exists, application criteria remain NOT TESTED. Internal verification success alone is insufficient.

Report source identity, policy, activation and behavior separately for each arm. One pair is diagnostic, not a reliability estimate; repeated paired trials and their resource allocation require separate agreement. All attempted trials and failures stay in denominators. The E2E owner reports coverage and independent acceptance; mechanism owners interpret and correct their own controller/grounding/schema implementations.
