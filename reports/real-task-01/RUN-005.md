## Diagnosis: two independent transport limits

The earlier canary change did not affect normal model requests. [mini.py](../../mini.py) still set `OLLAMA_TIMEOUT_SECONDS = 120` and passed it into the non-streaming HTTP request used for specification. Inspection located this independent constant and the actual request path rather than assuming the preflight setting applied globally.

The request used the same selected model and role-specific policy: Specifier context 4096 and output limit 1536, with `stream=False` and `think=False`. A tiny canary completing within 180 seconds is not evidence that this response can complete within 120 seconds.

Readiness queries after the failure showed the Ollama API still responded and the same model remained loaded. No extra diagnostic inference was needed. The evidence identifies an exhausted client deadline, but does **not** isolate slow generation, initial loading, scheduling or hardware as the ultimate timing cause. It also does not independently demonstrate cancellation of the provider's request after the client timed out.

## Minimal subsequent change

The normal request constant changed **120 → 600 seconds**, remaining finite. There was no change to model identity, sampling, context/output budgets, retry policy, Worker policy, grounding, safety checks or verifier. No fallback model or synthetic response was substituted.

The purpose was to let the known reachable local model complete an otherwise normal request before declaring transport failure. The change does not promise bounded whole-run duration: each request has its own deadline and an agent may make many requests. It also increases worst-case wait time when a server does not answer.

This is one of the runtime changes **published in PR #2**. It is distinct from the two local ingestion rewrites needed to reach this point in the historical experiment.
