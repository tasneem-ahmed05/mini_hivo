Run-002 tested whether the isolated application-building request could proceed after the Python 3.11 compatibility correction. It used the same source base, model `gemma4:e4b`, prompt, existing Python environment, browser configuration and experiment policies as Run-001. The only production delta at launch was the approved reentry expression correction. The host deadline was still **30.0 seconds per canary**; the separate normal provider deadline remained 120 seconds.

The fresh empty `runs/run-002/workspace` and non-clobbering `launch-run-002.ps1` preserved Run-001. Its actual CLI flags match [setup](EXPERIMENT-SETUP.md). The expected startup sequence was imports, dependency/workspace/model checks, all three bounded canaries, then `You>`. The task would only be submitted after that prompt.

## Observed sequence

1. Python imports succeeded, demonstrating that the preceding parse blocker was removed in a real CLI launch.
2. The launcher selected the intended empty workspace. Existing Ollama and the catalog entry for the selected model were available.
3. Host preflight began at `2026-10-20T20:23:28.044+00:00` and ended at `20:23:58.639+00:00` (23:23 local Africa/Cairo). Its recorded duration was **30.595 seconds**.
4. The first real model canary timed out. The report records **0 completed of 3 requested** canaries. It did not skip the first failure and proceed to the remaining calls.
5. The native terminal state was `HOST_PREFLIGHT_FAILED`; the stored failure reason was **`CANARY_PROVIDER_FAILURE`**, summary **`timed out`**, stage canary.
6. Python exited **2** before `You>`; outer PowerShell returned 0 for the same native-exit propagation limitation seen in Run-001. The Coin Courier prompt was **not submitted**.

Selected preflight fields, projected from the local report:

```json
{
  "status": "FAIL",
  "duration_seconds": 30.595,
  "canary_calls_completed": 0,
  "canary_calls_requested": 3
}
```

Only `.agent_host_preflight.json` was created inside the workspace. No task planning, Worker execution, application code, or browser verification occurred.

## Root cause and limits of the diagnosis

The observed blocker was the **client's finite canary transport deadline**. Model catalog availability and a responsive API did not guarantee that the first model response could finish within 30 seconds. The record does not isolate model loading, inference, resource scheduling, or another timing contributor. It does not establish an out-of-memory condition, GPU fault, or broken model.

The exact failure label matters: do not substitute `CANARY_TIMEOUT` for the recorded `CANARY_PROVIDER_FAILURE`. The transport wraps the underlying timeout as an HTTP transport failure, and the string `timed out` does not match a classification branch looking for `timeout`. No relabeling fix was applied in this experiment.

Client timeout also does not prove that provider-side inference was cancelled. Background completion/cancellation was not independently established. This is a startup infrastructure observation rather than a failed game-planning result.

## Follow-up correction and mechanism tests

Inspection of [host_preflight.py](../../hivo/host_preflight.py) and its call sites found the hard-coded `CANARY_TIMEOUT_SECONDS = 30.0`; no existing CLI/environment override was available. The authorized minimal change set it to **180.0**. It retained:

- Three canary calls and their exact expected response `HIVO_PREFLIGHT_OK`.
- Prompt `Reply with exactly: HIVO_PREFLIGHT_OK`.
- Context 512, output limit 32, temperature 0 and the same selected model.
- Two-second cooldowns, including the final cooldown.
- Resource monitoring, provider-error behavior and startup failure gates.

The original focused validation recorded:

```text
python -B -m unittest discover -s tests -p test_host_preflight.py -v
Ran 20 tests
OK
```

All 196 inspected Python files compiled in memory after the constant change. This proved syntax and existing deterministic preflight behavior, not a live model's timing. The actual live confirmation was deferred to Run-003.

Later PR preparation strengthened [host-preflight tests](../../tests/test_host_preflight.py) to assert that **180 seconds reaches transport** and all three calls/cooldowns remain active. The final PR suite has 21 tests, not the historical 20. [Fixes and validation](FIXES-AND-VALIDATION.md) gives exact final commands and negative-case coverage.
